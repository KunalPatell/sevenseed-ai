# Design Document: Sevenseed Platform Features Round 2

## Overview

This document describes the technical design for 13 requirements across Round 2 of the Sevenseed platform build: six new feature pages, five deep improvements to existing pages, one cross-venture component, and a print/export system. All deliverables are static HTML + CSS + vanilla JS files — no build tooling, no framework, no server-side rendering. Demo and simulated data replace live APIs everywhere, and `localStorage` provides all persistence.

---

## Architecture

The platform architecture is unchanged from Round 1:

```
sites/
  <venture>/
    style.css        ← venture-specific design tokens + shared component classes
    app.js           ← shared JS: preloader, nav scroll, theme toggle, scramble FX
    index.html       ← landing page (regenerated by site_builder/<venture>_builder.py)
    <feature>.html   ← standalone feature pages (NOT regenerated — hand-maintained)
    app/
      index.html     ← standalone React/Next export (not modified by Round 2 code)
site_builder/
  <venture>_builder.py  ← Python generator; nav links here survive redeploy
```

Each new feature page follows the **established template pattern**:

1. Inherits shared CSS variables and base component styles from `style.css`.
2. Loads `app.js` for preloader, theme toggle, and nav interactions.
3. Declares page-level `<style>` for feature-specific layout.
4. Declares page-level `<script>` for feature logic — all vanilla JS, no bundler.
5. Links to `style.css` and `app.js` via a relative path.

Nav link registration in `site_builder/<venture>_builder.py` is the critical step that makes new pages survive regeneration. Each builder contains a `nav_links` list or inline HTML block that is emitted into the nav — adding the link there is all that is needed.

## Components and Interfaces

### A. Triage Engine (symptom-checker.html)

The triage function maps symptom keywords to urgency levels using a lookup table:

```js
// Simplified structure
const TRIAGE_DB = {
  keywords: {
    chest_pain: { level: 'Emergency', conditions: ['Myocardial Infarction', 'Angina'], ... },
    fever:      { level: 'See Doctor', conditions: ['Influenza', 'Typhoid'], ... },
    headache:   { level: 'Home Care', conditions: ['Tension Headache', 'Dehydration'], ... },
    // ... 20+ entries
  }
};

function triage(symptomsText) {
  // Tokenise, look up each token, take highest urgency, merge conditions, build DO/DON'T
  return { level, conditions[], doList[], dontList[] };
}
```

**Urgency priority order**: Emergency > See Doctor > Home Care. If any keyword maps to Emergency, the result is Emergency.

### C. Donation Ledger (donation-ledger.html)

Static `DONATIONS` array (≥10 entries) is compiled into the page. The animated counter uses `requestAnimationFrame`:

```js
function animateCounter(el, target, duration) {
  const start = performance.now();
  function tick(now) {
    const p = Math.min(1, (now - start) / duration);
    el.textContent = '₹' + Math.floor(p * target).toLocaleString('en-IN');
    if (p < 1) requestAnimationFrame(tick);
  }
  requestAnimationFrame(tick);
}
```

Category proportions are calculated at runtime from the static array. The 80G receipt overlay is a hidden `<div id="receipt-overlay">` that is unhidden immediately before `window.print()` and re-hidden in the `afterprint` event.

### F. Resume Scorer Engine (resume-scorer.html)

ATS scoring uses keyword frequency against a built-in dictionary:

```js
const ATS_KEYWORDS = {
  technical: ['python', 'javascript', 'sql', 'react', 'aws', 'docker', ...], // 30+
  soft:      ['leadership', 'collaboration', 'communication', ...],          // 10+
  action:    ['developed', 'led', 'designed', 'optimised', 'delivered', ...] // 20+
};

function atsScore(text) {
  const lower = text.toLowerCase();
  let matched = 0, total = allKeywords.length;
  allKeywords.forEach(k => { if (lower.includes(k)) matched++; });
  return Math.round((matched / total) * 100);
}
```

Section detection uses regex heuristics:

```js
const SECTION_PATTERNS = {
  contact:    /(email|phone|linkedin|@)/i,
  summary:    /(summary|profile|objective)/i,
  experience: /(experience|employment|work history)/i,
  skills:     /(skills|technologies|tools)/i,
  education:  /(education|degree|university|college)/i,
};
```

### G. Cold-Start Banner Component

A single self-contained `<script>` block (no external deps):

```js
(function() {
  var attempts = 0, MAX = 10, DELAY = 3000, TIMEOUT = 3000;
  var banner = null;

  function showBanner(msg) {
    if (!banner) {
      banner = document.createElement('div');
      banner.id = 'cold-start-banner';
      banner.style.cssText = 'position:fixed;top:0;left:0;right:0;z-index:9999;' +
        'background:#92400e;color:#fef3c7;padding:10px 20px;text-align:center;font-size:14px;';
      document.body.prepend(banner);
    }
    banner.textContent = msg;
  }

  function hideBanner() {
    if (banner) { banner.remove(); banner = null; }
  }

  function attempt() {
    var ctrl = new AbortController();
    var timer = setTimeout(function() { ctrl.abort(); }, TIMEOUT);
    fetch('/api/health', { signal: ctrl.signal })
      .then(function(r) {
        clearTimeout(timer);
        if (r.ok) { hideBanner(); return; }
        throw new Error('non-ok');
      })
      .catch(function() {
        clearTimeout(timer);
        attempts++;
        if (attempts === 1) showBanner('Waking up the backend (free-tier cold start, up to ~30s)…');
        if (attempts >= MAX) {
          showBanner('Backend may be unavailable. Please try refreshing.');
          return;
        }
        setTimeout(attempt, DELAY);
      });
  }

  attempt();
})();
```

Typewriter effect uses `setInterval` at `Math.floor(1000 / 20)` = 50ms per character (≈ 20 chars/sec):

```js
function typewriter(el, text, onDone) {
  let i = 0;
  const iv = setInterval(function() {
    el.textContent += text[i++];
    if (i >= text.length) { clearInterval(iv); onDone && onDone(); }
  }, 50);
}
```

Markdown export uses a `<a>` element with `href = 'data:text/markdown;charset=utf-8,' + encodeURIComponent(content)` and programmatic `.click()`.

### K. Venture Dashboard Patches (venture-dashboard.html)

Filter logic runs on `input` events with a 0ms debounce (browser's native throttling is sufficient for ≤8 cards):

```js
filterInput.addEventListener('input', function() {
  const q = this.value.toLowerCase();
  cards.forEach(function(card) {
    const match = card.dataset.sector.toLowerCase().includes(q) ||
                  card.dataset.name.toLowerCase().includes(q);
    card.style.display = match ? '' : 'none';
  });
});
```

Recents queue maintains FIFO with max-3, implemented as unshift + slice:

```js
function pushRecent(venture) {
  let recents = JSON.parse(localStorage.getItem('ss_hub_recents') || '[]');
  recents = [venture, ...recents.filter(v => v.id !== venture.id)].slice(0, 3);
  localStorage.setItem('ss_hub_recents', JSON.stringify(recents));
}
```

## Correctness Properties

*A property is a characteristic or behavior that should hold true across all valid executions of a system — essentially, a formal statement about what the system should do. Properties serve as the bridge between human-readable specifications and machine-verifiable correctness guarantees.*

### Property 1: Triage urgency is always a valid level

*For any* non-empty symptom string, the triage function SHALL return a result whose `level` field is exactly one of `"Emergency"`, `"See Doctor"`, or `"Home Care"`.

**Validates: Requirements 1.2**

---

### Property 2: Triage results always contain sufficient output

*For any* non-empty symptom string that produces a triage result, the `conditions` array SHALL have length ≥ 2, `doList` SHALL have length ≥ 3, and `dontList` SHALL have length ≥ 3.

**Validates: Requirements 1.3, 1.4**

---

### Property 3: Reminder round-trip (add → persist → load)

*For any* valid reminder entry (non-empty name, dose, frequency, time), after saving the entry and re-reading `ss_pharmacy_reminders` from `localStorage`, the saved entry SHALL be present and structurally equivalent to the original.

**Validates: Requirements 2.2, 2.3**

---

### Property 4: Reminder deletion removes from store

*For any* set of reminder entries in `localStorage`, after deleting a specific entry, that entry SHALL NOT appear in the updated `ss_pharmacy_reminders` array.

**Validates: Requirements 2.7**

---

### Property 5: Category proportions sum to 100%

*For any* non-empty donation dataset, the sum of the Education, Food Relief, and Medical Aid category proportions SHALL equal 100% (within floating-point tolerance of ±0.5%).

**Validates: Requirements 3.4**

---

### Property 6: Volunteer skill-matching correctness

*For any* volunteer registration with skills set S and any opportunity catalogue, the set of highlighted opportunities SHALL be exactly those whose `requiredSkills` set intersects S — no more, no fewer.

**Validates: Requirements 4.4**

---

### Property 7: Volunteer registration round-trip

*For any* valid registration object, after saving to `localStorage` and reloading, the form fields SHALL be pre-filled with values equal to the original registration.

**Validates: Requirements 4.2, 4.7**

---

### Property 8: ATS score is always in valid range

*For any* resume text string (including empty, whitespace-only, or arbitrary Unicode), the `atsScore` function SHALL return a number in the inclusive range [0, 100].

**Validates: Requirements 6.2**

---

### Property 9: Section detection is always boolean

*For any* resume text string, the section completeness check SHALL return a result where each of the 5 section keys (contact, summary, experience, skills, education) maps to a boolean value (never `undefined` or `null`).

**Validates: Requirements 6.3**

---

### Property 10: Chat history round-trip

*For any* sequence of chat messages added to `localStorage` under `ss_gyan_history`, reloading the page SHALL render exactly that sequence of messages in the original order.

**Validates: Requirements 7.1, 7.2**

---

### Property 11: Explain-wrong-answer pre-fill is correctly templated

*For any* wrong-answer pair (question text Q, chosen option A), clicking the "Explain this answer" button SHALL pre-fill the chat input with a string that contains both Q and A verbatim.

**Validates: Requirements 7.4**

---

### Property 12: Topic tracker count is non-decreasing

*For any* topic T, the count shown in the topic progress tracker SHALL be ≥ 1 after the first message about T is sent, and SHALL increment by exactly 1 for each subsequent message about T.

**Validates: Requirements 7.5**

---

### Property 13: Wishlist round-trip (save → load)

*For any* product entry saved to `ss_emart_wishlist`, reloading the page SHALL display that entry in the Wishlist panel.

**Validates: Requirements 8.1, 8.2**

---

### Property 14: Wishlist removal is complete

*For any* saved wishlist item, after clicking Remove, that item SHALL NOT appear in either `localStorage` or the rendered Wishlist panel.

**Validates: Requirements 8.3**

---

### Property 15: Agent dispatch counter is monotonically increasing

*For any* sequence of dispatches to a given agent, the agent's `tasksCompleted` counter in `localStorage` SHALL be exactly equal to the number of dispatches performed since the key was first created.

**Validates: Requirements 9.3, 9.4**

---

### Property 16: Scan summary URL hash round-trip

*For any* scan summary object S, encoding S to a URL hash and then decoding that hash SHALL produce an object structurally equivalent to S (same defect counts, severity, and BOQ estimate).

**Validates: Requirements 10.1, 10.2**

---

### Property 17: Scan history length invariant

*For any* sequence of N scans (N ≥ 0), the `ss_breakdown_history` array in `localStorage` SHALL have length equal to `min(N, 5)` — never exceeding 5 entries.

**Validates: Requirements 10.3, 10.4**

---

### Property 18: Venture filter completeness

*For any* filter query string Q and venture catalogue, the set of visible venture cards SHALL be exactly those whose `name` or `sector` contains Q as a case-insensitive substring — no hidden cards should match Q, no visible cards should fail to match Q.

**Validates: Requirements 11.1**

---

### Property 19: Recents queue invariant

*For any* sequence of venture clicks, the `ss_hub_recents` array in `localStorage` SHALL have length ≤ 3, SHALL be ordered newest-first, and SHALL contain no duplicate venture IDs.

**Validates: Requirements 11.3**

---

### Property 20: Cold-start banner retry never exceeds cap

*For any* sequence of health endpoint failures, the Cold_Start_Banner SHALL invoke the fetch callback at most 10 times before stopping retries.

**Validates: Requirements 12.3, 12.5**

---

### Property 21: Cold-start banner hides on first success

*For any* scenario where the first N fetches fail followed by one success (1 ≤ N ≤ 9), the banner SHALL be visible after the Nth failure and SHALL be hidden (removed from DOM) after the success.

**Validates: Requirements 12.2, 12.4**

## Error Handling

| Scenario | Handling |
|---|---|
| Symptom input is empty | Inline validation error shown; triage not run |
| Reminder form field empty | Per-field red border + error text; save blocked |
| Volunteer form invalid | Per-field errors; save blocked |
| Resume text < 50 chars | Validation error; analysis blocked |
| `localStorage` quota exceeded | `try/catch` around all `setItem` calls; silent failure with console.warn |
| Notification permission denied | Button hidden or labelled "Enable in browser settings" |
| URL hash decode fails (malformed) | Error caught; results panel not rendered; informational message shown |
| Cold-start endpoint returns non-2xx | Treated as failure; retry triggered |
| Cold-start AbortController timeout | Treated as failure; retry triggered |

## Testing Strategy

This feature set spans UI rendering, data transformation functions, localStorage persistence, and simulated interactions. The appropriate test split is:

### Unit / Example-Based Tests
- Page file existence and nav link registration (smoke)
- `@media print` block presence (smoke)
- Specific UI states: Emergency CTA visibility, quiz results explain buttons, ecosystem gauge
- Animation trigger (SVG draw, counter ticker) — verify class/attribute applied
- Keyboard interactions: Enter sends chat, Ctrl+/ focuses input, Ctrl+Enter dispatches

### Property-Based Tests (PBT)

PBT applies to the pure-function data layer for this feature set. The recommended library for this project is **fast-check** (loaded via CDN for in-browser testing) or run offline with **Node.js + fast-check** for CI.

All 21 correctness properties above are implemented as property-based tests. Each test:
- Uses `fc.property(...)` with an appropriate arbitrary (strings, arrays, objects)
- Runs a minimum of **100 iterations**
- Is tagged with: `// Feature: sevenseed-platform-features-round2, Property N: <text>`

**PBT is NOT applied to:**
- Visual/animation checks (SVG stroke animation, counter ticker) — use snapshot or example tests
- Notification API scheduling — mock-based integration test
- Keyboard shortcut behaviour — example-based test

### Property Test Configuration

```js
// Example: Property 8 — ATS score range
fc.assert(
  fc.property(fc.string(), function(resumeText) {
    const score = atsScore(resumeText);
    return score >= 0 && score <= 100;
  }),
  { numRuns: 200 }
);
// Feature: sevenseed-platform-features-round2, Property 8: ATS score is always in valid range
```

### localStorage Isolation

Each property test that touches `localStorage` MUST mock the storage layer (pass a Map-backed mock to the storage functions) to prevent cross-test pollution.

### Integration Tests

- Notification permission grant/deny path (mocked Notification API)
- `window.print()` invocation (mocked)
- Markdown file download (mocked `<a>.click()`)
- Cold-start banner with mocked `fetch` returning various timing/status combinations
